# Product Rules V1

决策日期：2026-07-28

状态：已确认

适用范围：
- App 端事情与记录体验
- 管理后台内容、模板、资产、审核与权限设计
- 与事情定义、版本、复制、封存、记录、治理相关的后续数据库与接口演进

说明：
- 本文只记录已经明确“全部按建议确认”的 15 项产品规则。
- 本文不描述已实现状态，也不假设某个数据库表或代码路径已经存在。
- 如与旧文档冲突，以本文作为 V1 设计基线。

## PR-01 系统内置事情由平台维护，稳定身份、版本、下架不影响历史

规则：
- 系统内置事情由平台维护，不归家庭编辑。
- 系统内置事情必须有稳定身份和可追踪版本。
- 系统事情下架后，历史记录仍保留原始指向，不因下架而失去可读性。

约束：
- 不能把系统内置事情当作家庭可随意改写的私有内容。
- 不能让“当前版本”覆盖掉历史事实。

数据/后台影响：
- 后台需要区分系统事情与家庭事情。
- 系统事情必须能查看版本历史、当前状态和下架历史。

验收条件：
- 可以明确区分某条事情是否为系统内置。
- 能查看系统内置事情的版本历史与下架历史。
- 任一历史记录都不会因系统事情下架而失去关联。

## PR-02 家庭自定义事情家庭私有，家庭角色控制编辑，删除不删除历史记录

规则：
- 家庭自定义事情只属于创建它的家庭。
- 家庭内角色决定谁能编辑，默认不跨家庭共享。
- 删除家庭自定义事情不会删除既有历史记录。

约束：
- 不得默认跨家庭共享。
- 不得把家庭自定义事情纳入全局系统内容池。
- 删除动作不能顺带抹去历史完成记录。

数据/后台影响：
- 后台必须按家庭维度展示、筛选和管理这类事情。
- 家庭支持和内容治理需要保留家庭边界。
- 删除后仍需保留用于回看和审计的历史关联。

验收条件：
- 家庭自定义事情只在对应家庭范围内可见。
- 后台能清楚展示它的家庭归属和编辑权限边界。
- 删除事情后，相关历史记录仍可读。

## PR-03 系统事情可复制为独立家庭事情并保留 copied_from，V1 不做复杂家庭字段覆盖或自动同步

规则：
- 允许把系统事情复制成一个独立的家庭事情。
- 复制后必须保留 `copied_from` 关系。
- V1 只做复制，不做复杂家庭字段覆盖，也不做自动同步。

约束：
- 复制后的家庭事情是独立对象，不是对原系统事情的就地修改。
- V1 不引入家庭覆盖规则作为已支持能力。
- 不做复制后自动跟随系统版本变化的同步机制。

数据/后台影响：
- 后台需要有“复制为家庭事情”的动作。
- 需要显示复制来源，便于追溯和治理。
- 不应出现把复制等同于覆盖的界面或数据契约。

验收条件：
- 能从系统事情生成独立家庭事情。
- 复制后可看见 `copied_from` 来源关系。
- V1 不要求复杂字段覆盖或自动同步逻辑即可完成流程。

## PR-04 系统事情发布必填完整字段与发布校验

规则：
- 系统事情在发布时必须通过完整字段校验。
- 系统事情发布前必须满足发布所需的完整字段要求。

约束：
- 系统事情的发布标准高于家庭事情。
- 不能跳过发布校验直接对外生效。

数据/后台影响：
- 后台表单与校验规则要区分系统发布和家庭创建。
- 系统发布流程需要明确校验错误与缺失项。

验收条件：
- 系统事情发布前能拦截缺失字段。
- 校验结果能明确指出哪些字段不完整。
- 未满足要求的系统事情不能进入发布态。

## PR-05 家庭自定义事情仅标题和至少一种允许记录方式必填，支持快速创建后完善

规则：
- 家庭自定义事情的最小必填项是标题和至少一种允许记录方式。
- 允许先快速创建，再补充完善其他字段。

约束：
- 不得强制家庭自定义事情一次性填满系统级完整字段。
- 最小可用不等于无约束，仍需满足标题和允许记录方式。

数据/后台影响：
- 后台需要提供家庭快速创建入口。
- 后续编辑页要允许补全字段，而不要求重建对象。

验收条件：
- 家庭自定义事情可以用最小字段完成创建。
- 创建后可继续补全其他信息。
- 校验只强制标题和至少一种允许记录方式。

## PR-06 suggest_mode 与 allowed_capture_modes 分离，推荐必须属于允许集合，默认可允许四种

规则：
- 推荐记录方式 `suggest_mode` 与允许记录方式集合 `allowed_capture_modes` 必须分离。
- 推荐值必须包含在允许集合中。
- 默认允许集合可以包含文字、照片、视频、语音四种。

约束：
- `suggest_mode` 是推荐，不是允许集合的替代品。
- `allowed_capture_modes` 是约束边界，不能比推荐更窄到把推荐排除掉。

数据/后台影响：
- 后台需要同时编辑推荐值与允许集合。
- 校验层必须保证推荐值被允许集合覆盖。

验收条件：
- 任一事情都能单独配置推荐与允许范围。
- 保存时会校验推荐值属于允许集合。
- 默认配置可表达四种允许记录方式。

## PR-07 一次记录允许文字 + 多张照片 + 视频 + 语音等混合媒体，可保留 primary_capture_mode

规则：
- 一次记录允许文字与多种媒体混合出现。
- 一次记录可包含多张照片、视频、语音等组合。
- 记录可保留 `primary_capture_mode` 作为主采集方式。

约束：
- 记录模型不能只支持单一媒体类型。
- 主采集方式只是主轴，不排斥同次记录里存在其他内容形态。

数据/后台影响：
- 后台审核和详情页需要同时展示文字与媒体附件。
- 记录数据结构需要表达混合内容和主采集方式。

验收条件：
- 一条记录可以同时包含文字、照片、视频和语音中的多种内容。
- 可以查看这条记录的主采集方式。
- 不需要拆成多条记录才能保存一次混合内容。

## PR-08 系统插画归属事情版本，不存在独立系统资产库，motif 仅回退

补充决策：2026-07-31

规则：
- 系统插画直接归属于事情版本，是版本化内容事实的一部分。
- 系统插画不再拥有独立系统资产库或独立资产实体。
- 不以系统资产列表作为后台新契约；旧客户端如需过渡，可使用从版本字段派生的兼容 view / RPC。
- motif 只作为无可用系统插画时的回退方案。

约束：
- 插画不是全局资产实体，不能脱离事情版本单独治理、发布或复用。
- 版本必须能保存插画的 `storage_path`、`mime_type`、`width`、`height`、`alt` 和 `metadata`。
- 新版本继承旧版本插画时必须形成版本快照，不能让后续编辑改写历史版本事实。
- motif 不应替代正式版本插画，也不应成为主内容插画的长期承载方式。

数据/后台影响：
- 后台事情版本编辑页直接编辑插画字段。
- 审核页查看的是版本插画快照，而不是独立资产记录。
- 从旧系统资产引用迁移到版本字段前必须验证引用已回填；存在未归属系统资产时不得删除原数据。

验收条件：
- 任一系统事情版本能直接读到插画路径、文件类型、尺寸、替代文本和元数据。
- 历史版本插画不会因当前版本变更而被改写。
- 不存在面向新后台契约的系统插画资产列表。
- 可识别某个事情版本是否在使用 motif 回退。

## PR-09 家庭上传封面家庭私有，不可跨家庭复用，治理查看受限

规则：
- 家庭上传封面属于家庭私有资产。
- 家庭上传封面不可跨家庭复用。
- 治理查看该类封面时需要受限访问。

约束：
- 不得默认公开给其他家庭使用。
- 不得把家庭封面当作系统公共资产。
- 不得默认对所有管理员开放无理由查看。

数据/后台影响：
- 后台需要在家庭范围内管理封面。
- 系统事情版本插画与家庭私有封面要分开表达。
- 治理查看必须记录理由和审计。

验收条件：
- 家庭封面只在对应家庭范围可见或可用。
- 后台能区分系统插画与家庭上传封面。
- 管理员查看家庭上传封面时有受限治理路径。

## PR-10 系统事情采用草稿/发布/新版本/下架/历史版本治理

规则：
- 系统事情采用草稿、发布、新版本、下架、历史版本的治理方式。
- 新版本不是覆盖历史，而是形成可追踪的版本链。

约束：
- 草稿不应被当作已发布内容对外生效。
- 下架不应抹去历史版本。

数据/后台影响：
- 后台需要明确版本状态与版本切换动作。
- 历史版本必须可回看、可审计。

验收条件：
- 可以看到系统事情的草稿、已发布、新版本、下架与历史版本状态。
- 任一已发布内容都能追溯其版本链。
- 下架后历史版本仍可查询。

## PR-11 历史完成记录绑定 activity_id、activity_version_id 和必要快照，不被新版本改写

规则：
- 历史完成记录在完成时必须绑定 `activity_id`、`activity_version_id` 和必要快照。
- 新版本不能改写已经完成的历史记录事实。

约束：
- 历史完成记录不能只依赖可变标题或当前最新定义。
- 必要快照必须足以还原当时的记录语义。

数据/后台影响：
- 后台记录详情需要展示版本与快照信息。
- 版本变更不能破坏已存在记录的可读性。

验收条件：
- 任一完成记录都能追溯到对应 `activity_id` 和 `activity_version_id`。
- 版本更新后，旧记录仍能按当时快照读取。
- 新版本不会改写旧记录的绑定信息。

## PR-12 封存最终是记录级选择，事情只提供默认建议

规则：
- 封存的最终决策发生在记录级。
- 事情层只提供封存默认建议，不替代记录级决定。

约束：
- 事情定义不能强制覆盖每次记录的封存结果。
- 记录级封存决策必须保留独立性。

数据/后台影响：
- 后台需要区分事情默认规则与记录最终状态。
- 审核和历史回看必须以记录实际封存结果为准。

验收条件：
- 一条记录可以有自己的封存结果。
- 事情层的默认建议不等于记录最终状态。
- 记录详情能清楚显示最终封存选择。

## PR-13 家庭自定义事情默认不常规人工审核，仅举报/风险/申请公开等治理场景介入

规则：
- 家庭自定义事情默认不进入常规人工审核流程。
- 仅在举报、风险、申请公开等治理场景下介入。

约束：
- 不得把家庭自定义事情默认纳入与系统内容同等的常规审核队列。
- 人工介入必须有明确治理触发条件。

数据/后台影响：
- 后台审核中心需要按对象类型分流。
- 常规内容审核和家庭自定义事情治理要分开。

验收条件：
- 家庭自定义事情不会默认出现在常规审核队列。
- 若需要人工介入，必须能识别治理原因。

## PR-14 家庭完成记录默认私有，管理员查看需治理理由和审计

规则：
- 家庭完成记录默认私有。
- 管理员查看家庭完成记录必须具备治理理由，并留下审计痕迹。

约束：
- 管理员不能以一般浏览为默认前提查看家庭完成记录。
- 查看动作必须与治理场景绑定。

数据/后台影响：
- 后台需要显示查看理由和审计记录。
- 权限系统必须支持“可看但需理由”的治理式访问。

验收条件：
- 家庭完成记录默认不向管理员开放为普通浏览对象。
- 管理员访问能记录治理理由。
- 审计日志可追踪查看行为。

## PR-15 四类管理员最小权限：内容编辑、内容审核、家庭支持、系统管理员

规则：
- 管理员角色采用四类最小权限集合：
  - 内容编辑
  - 内容审核
  - 家庭支持
  - 系统管理员

约束：
- 角色设计以最小权限为原则。
- 不得默认给所有管理员同等能力。

数据/后台影响：
- 后台导航、页面操作和按钮权限必须按角色分区。
- 审计日志需要记录角色与操作的对应关系。

验收条件：
- 四类角色边界明确。
- 每个角色可执行的动作有清晰上限。
- 不存在未定义的隐式超级角色混入常规流程。

## 通用约束

- 来源与归属必须在后台可追踪，但不作为独立编号规则重复展开。
- 历史记录优先保真，不能被后续版本或删除动作改写事实。
- V1 只确认上述 15 条规则，不额外引入未确认的家庭覆盖、自动同步或隐藏审核逻辑。
